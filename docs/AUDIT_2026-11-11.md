## High priority findings

1. **Offline billing is not operationally complete.** One pending bill blocks further invoices. No pending edit/cancel/conflict resolution exists. A changed price, deleted item or stock shortage can leave the counter blocked indefinitely. Evidence: offline-bill.ts, PendingOfflineBill.tsx and createBill's pending check.
2. **No cold offline startup.** No service worker/app shell or cached authenticated catalog boot path. Loaded-page queue is not a substitute for opening the POS after a restart with no network. navigator.onLine also does not detect every backend outage; those errors retain a draft rather than queue a sale.
3. **Subscription enforcement differs across layers (source finding).** BillingWorkspace checks subscription usability; PosAuthGuard checks active membership/user/business but not subscription expiry, and createInvoice has no matching subscription check. Direct authenticated API use may differ from UI restrictions. Not exploited against production.
4. **Fractional quantity editor bug (source finding).** BillingWorkspace.setQuantity clamps with Math.max(1,...). Editing 0.5 kg becomes 1, while AI/backend permit decimals. Fractional stock below one can also produce inappropriate quantities.
5. **Recovery is not robust multi-tab storage.** localStorage compare-then-set is not atomic across browser tabs. Shared draft key has no exclusive transaction. Only some recovery fields are validated. Account scoping helps but does not prove safe multi-tab behavior. Browser acceptance tests are still needed.
6. **Device storage failure blocks online invoices.** createBill requires local recovery save and reads IndexedDB even for online sales. A quota/private-mode/storage failure can stop otherwise valid online billing. Need an explicit, safe degraded mode.
7. **Product saves lack retry identity in the AI path.** New product requests do not send a stable product ID although the API accepts one. If a response is lost, a repeat can create duplicates. Invoice retries have stronger protection.

## UX and AI gaps

- Only a portion of the flow is Hindi: product field labels, many validation errors and billing context remain English. Low-literacy usability has not been tested with shopkeepers.
- Bill speech readback lists item names/quantities but does not read the payable total, selected customer/payment/discount, or existing cart contents. Direct confirmation can therefore save more than the spoken preview describes.
- Product stock/unit/tax can default to 0/pcs rather than shop-specific defaults or a clear clarification question.
- One new product per request; no single-command new-customer + multiple-new-products + invoice workflow.
- AI catalog limited to first 500 active products; large catalogs can produce unresolved items even when they exist.
- No conversational corrections (“remove oil”, “make it three”) tied to the current draft.
- Offline recognition not implemented; speech recognition and synthesis availability/language quality depend on device/browser. Hindi audio and noisy-shop microphone behavior remain untested.
- AI quota/circuit breaker and tenant-level usage budgeting remain incomplete. Provider latency is not bounded by the two-click UI target.

## Payments, deployment and coverage gaps

- Cashfree subscription/webhook code exists, but no sandbox checkout, verified webhook, failed-payment, refund, reconciliation or settlement acceptance test was run. Do not equate code presence or configured variable names with a finished POS payment gateway.
- Card/UPI method selection in ordinary invoice creation records an operator assertion; it is not a verified gateway transaction.
- Frontend is local development hosting. It stops when the process/machine stops; it is not a deployed storefront/counter application.
- R2 was disabled in the deployed configuration earlier; upload/download readiness has not been established.
- Android auth configuration has a preflight failure; Android voice/offline/printing feature parity is not established.
- Android Kotlin compilation warns about inferred intersection types in OfflineDatabase.kt:580 and deprecated system-bar APIs in LaunchDesign.kt:247-248. These are warnings, not observed runtime failures.
- Generated Android .gradle/app/build files are already tracked in Git; running a build modifies hundreds of tracked artifacts despite ignore rules. Remove generated outputs from version control in a separate cleanup, preserving reproducible source/configuration.
- Web test script only echoes “web tests pending”; no automated full browser regression suite currently runs through normal test command.
- Baseline regex security scan is not a penetration test. Staff/admin routes, revoked tokens, tenant switching, concurrent sales, refunds/returns, ledgers/reports, printer disconnects, backup restore and gateway webhook replays need dedicated coverage.

## Recommended repair sequence

1. Set up an isolated active test business; do not bypass the live trial or pollute real sales.
2. Fix fractional quantities, server-side entitlement policy and recoverable queue conflicts.
3. Build transactional multi-bill offline storage, cached startup, authenticated reconciliation, and inspectable local receipts.
4. Finish Hindi prompts/readback, totals and clarification/correction flow; test on Android and Windows with actual users.
5. Complete Android configuration/build/device checks and a reproducible browser regression suite.
6. Integrate and test gateway sandbox payments, failure/refund paths and reconciliation, then deploy the frontend.

Current assessment: working prototype with passing core backend checks; not yet ready as the sole daily billing system for a shop that must survive network/device failures.
